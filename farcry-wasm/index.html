the engine boots

the core of the engine starts up inside one WebAssembly module now, and it sits in its main loop without crashing. lua works too. it was polite and said hello.

nothing draws yet though. i’m using the engine’s null renderer, which takes every draw call and shows nothing, so for now it only runs in node.

working: startup, console and file system, Lua scripts, AI, entities, animation, 3D engine init, and the main loop.

not yet: reading game data (every path uses backslashes), input, sound, the actual game code, and a renderer. physics, movie and networking are just switched off for now.

the original game is a pile of separate DLLs that load each other while it runs, and WebAssembly can’t do that. so each one is a static library now and everything gets linked into one file. for every module i did the same three things:

  • build it as a static library
  • swap the “load the DLL, look up CreateX” code for a direct call to CreateX
  • delete the duplicate globals each DLL kept its own copy of, like GetISystem()
stuff the compiler didn’t like 
-fexceptions                   engine throws C++ exceptions
-fdelayed-template-parsing     MSVC lets templates call functions declared later
std::auto_ptr                  removed from C++17, now std::unique_ptr
__finite()                     glibc-only, shimmed with __builtin_isfinite
sys/io.h                       glibc-only header, skipped on wasm
X::X() inside a constructor    MSVC accepts a no-op, clang rejects it

what’s next

  • file paths. the engine asks for things like fcdata\localized\english.pak with backslashes. those need converting, and the data files have to be visible to the subsystem/module (whatever it's called).
  • input and sound. the originals use DirectInput and FMOD, so those get SDL and a stub or OpenAL.
  • the game module. the bad boy that's really hard to make
  • a real renderer. the original OpenGL path leans on NVIDIA-only extensions that WebGL doesn’t have, so this means writing a new WebGL backend.
